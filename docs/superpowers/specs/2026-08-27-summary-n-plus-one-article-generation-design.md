# SummaryTask 动态 N 项目文章生成设计

## 目标

把 `SummaryTask` 从“一次模型调用生成整篇动态 Top N 文章”调整为“动态 N 次项目生成调用 + 1 次全局综合调用”。管理台的“本期项目数量”继续决定周榜记录数；当实际周榜包含 N 个项目时，任务生成 N 个项目章节和 N 份生图简报，最终仍只保存一篇完整文章。

最终文章顺序固定为：

1. 开篇总结；
2. 本周主线；
3. N 个项目章节，每个章节依次包含项目概述、项目图片、技术特点、机制拆解和工程启发；
4. 全文末尾的跨项目工程启发。

本次不增加数据库字段，不改变审核、图片、视频、排版和微信公众号草稿接口，也不把 N 写死为 5 或 6。

## 当前问题

当前 `SummaryTask` 把全部项目证据放入一次 DeepSeek 请求，让模型同时完成标题、摘要、完整正文和结构化项目简报。随着 N 增加，单次输出更长，项目之间容易互相污染，项目说明也容易退化为榜单式罗列。模型还需要同时遵守整篇文章结构和每个项目的视觉合同，任一项目出错都会导致整份长 JSON 重生成。

工作区已有改动已经引入 `project_briefs`、真实节点和关系校验。本设计保留这条方向，但把每份项目简报移到对应项目的独立生成调用中，让正文证据和生图语义在同一轮内产生。

## 调用架构

### 项目生成阶段

`SummaryTask` 按当期 `rankings` 顺序执行 N 次项目调用。每次调用只接收一个项目的榜单数据、README 摘录和已加载的 `github-project-blog` Skill，不得看到其他项目的证据。

每次调用返回一个 JSON 对象，只包含：

- `repository_full_name`：必须与当前项目完全一致；
- `overview_text`：项目概述；
- `technical_features_markdown`：技术特点；
- `mechanism_breakdown_markdown`：机制拆解；
- `engineering_insights_markdown`：该项目的工程启发；
- `project_brief`：包含 `summary_text` 和一份 `visual_brief`。

项目调用按排名顺序串行执行。该取舍优先保持调用追踪、限流行为和失败定位清晰；后续只有在真实运行数据显示延迟不可接受时，才单独评估有限并发。

### 全局综合阶段

全部项目结果通过校验后，再执行 1 次全局综合调用。该调用读取本期榜单数字和已经验证的项目结果，只负责生成：

- `title`；
- `digest`；
- `opening_markdown`：标题后的开篇总结；
- `weekly_theme_markdown`：`本周主线` 内容；
- `closing_markdown`：全文末尾的跨项目工程启发。

全局调用不再重写项目正文或视觉简报，避免综合阶段改变项目事实。

当 N=6 时，正常路径共执行 7 次主要 LLM 调用。每个调用最多允许 1 次质量修复重试，因此最坏情况下执行 14 次调用。重试只修复当前失败单元，不重放已经通过的项目调用。

## 文章拼装

模型只生成内容字段，标题层级、项目顺序和固定标签由 `SummaryTask` 确定性拼装：

```text
{opening_markdown}

### 本周主线
{weekly_theme_markdown}

### Top N 项目拆解

#### 项目 1：owner/repository
{overview_text}
**技术特点**
{technical_features_markdown}
**机制拆解**
{mechanism_breakdown_markdown}
**工程启发**
{engineering_insights_markdown}

...按排名重复 N 次...

### 工程启发
{closing_markdown}
```

`ArticleLayoutService` 在项目标题后的第一个正文块之后插入对应项目图片，因此 `overview_text` 后自然形成“项目概述 -> 项目图片 -> 三个教学分点”的阅读顺序。正文不输出图片占位文字。实现验证发现旧的 `Top {rank}` 匹配会把“Top N 项目拆解”误判成排名 N 的项目标题，因此项目匹配保留仓库名、`项目 N` 和 `第 N`，取消 `Top N` 匹配；排版与手动 GitHub 图片升级均遍历完整 `image_prompts`，不再截断为前 5 个项目。

## 项目内容合同

### 项目概述

每个 `overview_text` 必须用平实语言回答四件事：

1. 本周新增多少 stars；
2. 当前总 stars；
3. 项目解决什么问题或提供什么能力；
4. 适合放进什么使用场景。

stars 与本周增长必须保留数据库中的精确数字，不改写成模糊量级。概述不承担详细机制讲解，也不把 stars 当成项目质量证明。

### 三个可见分点

文章只显示三个固定分点，避免七段模板把文章写成问答清单。`github-project-blog` Skill 使用下面的内部检查关系保证教学深度：

- `技术特点`：项目整体定位、解决的问题、整体架构、模块划分和模块职责；
- `机制拆解`：入口到输出的数据流、关键类或文件、入口函数、模块依赖、强弱耦合及同步异步关系；
- `工程启发`：技术难点、设计取舍、潜在坑点、使用边界和源码阅读顺序。

只有输入证据包含真实路径、类名、函数名或调用关系时，才能写关键源码和耦合结论。证据不足时直接说明当前 README 摘录没有展开，不得用常见目录名、框架惯例或相似项目补全。

正文少贴源码。只有能够帮助解释核心逻辑时才使用短代码片段或伪代码，重点说明输入、决策、状态变化和输出。

## 生图合同

每个项目调用同时生成一份 `visual_brief`，所以项目调用数、项目章节数、`image_prompts` 数量始终都等于 N。

每个项目只生成一张教学图。图内同时表达：

- 3 到 4 个来自项目正文的真实模块或步骤；
- 模块之间的架构位置或职责边界；
- 从入口到输出的一条主数据流；
- 证据明确时才出现的强耦合、弱耦合、同步调用、异步调用或事件推送。

生图简报不得使用“输入、核心、处理、输出、任务、计划、执行、反馈”等脱离项目证据的占位节点。最终供应商 Prompt 仍由 `ImagePromptDesignService` 编译，`SummaryTask` 不生成 Seedream 参数或视觉样式说明。

## 文风合同

`github-project-blog` Skill 继续负责事实边界和技术教学方法，并吸收 `humanizer` 的以下写作约束：

- 使用直接、平实的技术讲解，不写销售话术和宏大趋势判断；
- 不使用“赋能、解锁、颠覆、全面解析”等空泛词；
- 不连续使用“不是 X，而是 Y”或戏剧化短句；
- 不虚构专家、行业共识、性能数据或应用案例；
- 不用标题后的第一句重复标题；
- 不为了形式强行补足事实不足的源码、模块和依赖分析；
- 保留事实、数字、名称、排名和证据限定，不通过润色改变技术结论。

三项固定分点是产品结构要求，不扩展为更多整齐划一的小标题。段落长短跟随内容，避免每个项目出现完全相同的句式。

## 校验与失败处理

每个项目结果独立校验：

- 仓库全名与当前排名一致；
- 概述原样包含当前 stars 和本周增长；
- 三个内容字段非空；
- 不含 URL、项目地址、第一人称和禁用营销表达；
- `project_brief` 节点与关系完整，且项目名、节点和关系满足事实合同。

全局结果独立校验标题、摘要、开篇、本周主线和结尾字段，并检查没有遗漏或新增项目事实。

某个调用首次不合格时，只携带该调用的事实输入和具体错误执行一次修复请求。第二次仍不合格则整个 `SummaryTask` 失败，不写入半篇文章或部分 `generated_contents`，保持现有原子失败语义。

模型调用 trace 至少记录阶段、项目排名、仓库名和尝试次数，便于区分 `project_generation`、`project_repair`、`global_synthesis` 和 `global_repair`。

## Skill 与代码边界

- `.agents/skills/github-project-blog/SKILL.md`：规定教学分析、单项目章节和全局综合的写作方法，不负责业务调用与存储；
- `src/tasks/summary_task.py`：读取动态 N、执行 N+1 调用、校验结果、拼装文章并保存；
- `src/services/media_creative_brief_service.py`：继续规范化项目视觉节点与关系；
- `src/services/image_prompt_design_service.py`：继续把视觉简报编译为最终生图 Prompt；
- `src/services/article_layout_service.py`：复用项目首段后插图行为，取消会误匹配总标题的 `Top {rank}` 项目标记，并按动态 N 处理全部项目图片；
- `src/services/github_image_upgrade_service.py`：手动图片升级同样消费全部 N 份项目图片合同；
- `scripts/verify_summary_depth_contract.py` 及相关测试：验证动态 N、调用次数、文章顺序、事实数字、三分点和图片数量。

## 验证标准

离线验证至少覆盖：

1. N=1、N=3 和 N=6 时，项目调用次数分别为 1、3 和 6，全局调用始终为 1；
2. 最终项目标题、章节和生图简报数量都等于 N，顺序与 `rankings` 一致；
3. 每个项目呈现“概述 -> 图片插入位置 -> 技术特点 -> 机制拆解 -> 工程启发”；
4. 概述包含精确的本周增长、总 stars、项目作用和使用场景；
5. 全文只出现一个开篇总结、一个本周主线和一个末尾工程启发；
6. 任一项目第二次校验仍失败时不入库，已通过项目不重复调用；
7. `image_prompts` 数量等于 N，并且每份简报同时包含架构节点与主数据流；
8. Skill 与提示词不写死项目数量，不引入运行时 `humanizer` 依赖；
9. Python 编译、SummaryTask 合同验证及相关测试全部通过。

## 范围边界

- 不新增数据库迁移；
- 不改变管理台的 N 配置来源；
- 不增加每个项目的图片数量；
- 不修改视频、音频、审核、交付或生产部署流程；
- 不在本次引入并发、缓存、断点续跑或部分成功持久化；
- 未经单独授权不部署到生产环境。
