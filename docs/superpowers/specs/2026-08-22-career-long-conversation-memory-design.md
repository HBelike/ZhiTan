# 求职助手长对话记忆设计

> 历史说明：本方案已被 2026-08-26 批准的《求职助手长期记忆与动态上下文压缩 V2 设计》取代。本文仅保留为决策演进记录，不再作为实施依据；后续实现、验收和配置均以 V2 设计为准。

## 目标

将求职助手从“数据库保存完整消息、模型只读取最近约两轮”改造成可持续压缩的单会话长对话。首期只建设两层记忆：最近完整轮次原文和一个带覆盖游标的结构化滚动摘要。系统必须在固定 Token 预算内保持上下文连续，同时保留全部脱敏原始消息作为可追溯事实源。

本设计参考 nanobot 的 Token 预算、增量压缩游标和失败不丢原文原则，但不引入 Dream、向量召回或模型自行维护的跨会话用户画像。参考资料：

- <https://github.com/HKUDS/nanobot/blob/main/docs/guides/ai-agent-memory.md>
- <https://github.com/HKUDS/nanobot/blob/main/nanobot/agent/memory.py>
- <https://github.com/HKUDS/nanobot/issues/3973>
- <https://github.com/HKUDS/nanobot/issues/4212>

## 已确认决策

- 首期优先支持单个会话持续数百轮，不建设跨会话自由事实库。
- 原始脱敏消息是唯一事实源；摘要是可丢弃、可重建的派生数据。
- 上下文按 Token 预算选取完整用户—助手轮次，不再按固定消息条数读取。
- 使用一份结构化滚动摘要，不同时建设分段摘要表，避免重复存储和多套压缩状态。
- 旧历史超过阈值时，在生成本轮回复前压缩；普通轮次不额外调用摘要模型。
- 摘要调用失败、返回非法结构或发生并发冲突时不更新摘要、不推进游标，用户回复链路继续降级运行。
- 不启用 pgvector 历史召回。只有长对话评测证明滚动摘要无法找回必要旧细节时，再单独设计召回层。
- 不增加 `confidence` 分数。用户事实和助手建议在摘要结构中分栏保存，禁止把助手推断提升为用户事实。
- 不新增用户端记忆管理页面，不进行手机端专项改造。

## 非目标

- 不让新会话自动读取其他会话中的自由对话事实。
- 不复制候选人档案、目标岗位档案或 `/offer` 进度数据。
- 不保证逐字保留无限历史；较早内容只保留结构化关键信息，原文仍可从数据库和历史页面读取。
- 不引入新的任务队列、向量数据库、Embedding 服务或第三方记忆框架。
- 不修改当前消息脱敏和原始附件删除边界。

## 当前问题

`CareerResponseRunner._build_prompt()` 当前查询最近 6 条消息。本轮用户消息已经先持久化，随后又在 Prompt 构建时被过滤，因此模型实际最多读取 5 条旧消息，通常只有两个完整轮次和一条孤立消息。每条旧消息还会在 1600 字符处截断。

数据库中的 `messages` 已保留完整脱敏历史，`session_summaries` 表和 `upsert_redacted_summary()` 也已经存在，但摘要没有覆盖游标、结构版本和读取链路，不能安全参与 Prompt。

## 总体架构

新增独立的 `ConversationMemoryService`，只负责三件事：估算 Token、在需要时合并滚动摘要、组装可注入 Prompt 的记忆上下文。`CareerResponseRunner` 仍负责模型路由和最终回答，不直接实现压缩算法。

```text
脱敏 messages（唯一事实源）
        │
        ├── session_summaries（覆盖到某条旧消息的结构化滚动摘要）
        │
        └── 覆盖游标之后的完整轮次
                    │
                    ├── 最旧完整轮次达到阈值：合并进摘要
                    └── 最近完整轮次：以原文进入 Prompt
```

每轮调用链：

```text
用户消息脱敏并持久化
  -> 解析本轮模型
  -> ConversationMemoryService.prepare()
       -> 读取当前摘要和游标后的历史
       -> 排除本轮尚未完成的用户消息
       -> 按 turn_id 形成完整用户—助手轮次
       -> 必要时压缩最旧轮次并以乐观锁保存摘要
       -> 在历史 Token 预算内选择最近完整轮次
  -> 组装系统规则、摘要、最近原文、当前用户输入
  -> 生成并持久化助手回复
```

当前轮次直到助手回复成功后才成为下一轮可压缩的完整轮次。失败或取消的 Turn 不进入摘要。

## Token 预算

首期不把上下文窗口写进每个模型档案，以免同时扩张模型设置 API、数据库和前端。统一在 `config/career_assistant.yaml` 的 `response_generation` 中增加：

```yaml
history_token_budget: 12000
summary_trigger_tokens: 8000
recent_turns_target: 8
summary_max_characters: 8000
```

- `history_token_budget` 只约束“滚动摘要 + 历史原文”，不包含系统规则、Skill、简历、JD 和当前输入。
- `summary_trigger_tokens` 控制游标后完整旧轮次达到多少 Token 时触发压缩。
- `recent_turns_target` 表示压缩时尽量留下的最近完整轮次，不是可以突破 Token 预算的硬下限。
- `summary_max_characters` 是摘要持久化和注入上限。

Token 使用纯本地确定性估算，不调用 Provider tokenizer。首期抽取面经切片器的字符估算逻辑为共享工具，并为 ChatMessage 的角色和分隔符预留固定开销。预算必须优先于目标轮数：单轮特别长时宁可少保留轮次，也不能无限扩大 Prompt。

## 结构化滚动摘要

`session_summaries.summary_text` 保存经过服务端校验的紧凑 JSON 字符串，不同时保存一份重复 JSONB。Schema 固定为 `career-conversation-summary-v1`：

```json
{
  "schema_version": "career-conversation-summary-v1",
  "user_stated_facts": ["用户明确表达、且仅对本会话有效的事实"],
  "current_goals": ["当前求职目标"],
  "decisions": ["已经确定的选择"],
  "open_loops": ["后续仍需处理的问题"],
  "assistant_suggestions": ["助手已经给过但用户未必接受的建议"],
  "corrections": ["用户对早先信息的明确修正，以新信息为准"],
  "companies": ["对话涉及的公司"],
  "roles": ["对话涉及的岗位"]
}
```

所有字段必须存在且只能是字符串数组。服务端限制数组数量、单项长度、总字符数和 Schema 版本，并去除空白与精确重复项。摘要 Prompt 按 `user`、`assistant` 明确标注来源，并遵守以下约束：

1. 只有用户原话能够进入 `user_stated_facts`、`current_goals`、`decisions` 和 `corrections`。
2. 助手提出的判断和建议只能进入 `assistant_suggestions`。
3. 当前简历和岗位档案仍是更高权威来源；摘要不能覆盖它们。
4. 新的明确纠正覆盖旧说法，旧说法不得继续保留为并列事实。
5. 不补全姓名、联系方式、证件、地址等已被脱敏的信息。
6. 合并时同时输入上一版摘要和本次待压缩完整轮次，输出完整的新快照，而不是差量补丁。

Prompt 注入时使用明确标签“以下是服务端从较早脱敏对话生成的派生记忆，仅用于延续上下文；如与当前用户输入、简历或岗位档案冲突，以后者为准”，防止摘要取得更高指令优先级。

## 持久化与并发

通过新迁移扩展 `career_assistant.session_summaries`：

- `covered_through_message_id UUID NULL`：最后一条已经纳入摘要的助手消息；
- `summary_schema_version TEXT NOT NULL DEFAULT 'career-conversation-summary-v1'`；
- 复用现有 `summary_version` 作为乐观锁版本；
- 继续要求 `contains_sensitive_data = FALSE`。

不增加处理中状态。摘要模型调用在数据库事务之外执行；保存时执行条件更新：只有数据库里的 `summary_version` 和 `covered_through_message_id` 仍与读取快照一致时才写入并递增版本。并发请求中较晚完成但基于旧快照的结果会被丢弃，不能覆盖新摘要。

已有摘要若没有覆盖游标或 Schema 版本不匹配，视为不可证明覆盖范围的旧派生数据，不注入 Prompt；第一次达到压缩阈值时从原始消息重新生成。

删除会话仍通过现有级联删除摘要。历史消息不因压缩而删除或改写。

## 压缩边界

`ConversationMemoryService` 从摘要游标之后读取消息，并按以下规则形成候选轮次：

- 排除当前 `active_turn.id`；
- 只接受同一 `turn_id` 下恰有用户消息且有助手消息的轮次；
- 保持数据库创建时间顺序；
- system/tool 消息不进入首期对话摘要；
- 失败、取消或尚未完成的 Turn 不进入候选集合；
- 压缩边界只能落在一个完整轮次的助手消息上。

当候选完整轮次总量超过 `summary_trigger_tokens`，服务只压缩最旧前缀，并尽量留下最近 `recent_turns_target` 个完整轮次。若除保留目标外没有可压缩前缀，则本轮不调用摘要模型，直接由预算选择器保留能容纳的最近完整轮次。

摘要成功保存后重新读取最新摘要和游标后的原文，避免用本地假定状态组装 Prompt。

## Prompt 组装顺序

最终 ChatMessage 顺序保持：

1. 求职助手系统规则；
2. 本轮激活 Skill 的受控说明；
3. 可用时注入一条派生会话摘要 system 消息；
4. 摘要游标后的最近完整用户—助手轮次；
5. 当前用户输入，以及本轮附件、简历、JD 和面试证据。

最近历史从新到旧按完整轮次装入预算，再恢复为正向时间顺序。单条消息不再使用 1600 字符硬截断；如果一个完整轮次本身无法进入剩余预算，则跳过该轮，不构造半轮历史。

## 错误处理与降级

- 摘要模型网络错误、限流或超时：记录不含正文的错误类别，不更新摘要；继续使用已有有效摘要和预算内最近原文回答。
- 模型返回非 JSON、字段缺失、类型错误或超限：视为无效摘要，不更新游标。
- 并发条件更新失败：丢弃本次派生结果，重新读取胜出的摘要组装 Prompt。
- 数据库摘要读取失败：不阻断原有模型回复；只使用预算内最近原文，并记录记忆组件错误。
- 没有任何有效摘要且旧原文超出预算：保留最新完整轮次，较老内容本轮不注入，但原始消息仍在数据库中。

记忆降级不得转化为整个 Turn 的模型失败。Trace 只记录摘要版本、覆盖消息数量、估算 Token、是否触发压缩、结果状态和错误码，不记录对话正文或模型原始摘要。

## 组件与文件边界

- 新建 `src/career_assistant/conversation_memory.py`：Schema 校验、Token 估算、完整轮次分组、压缩选择和 Prompt 记忆结果。
- 扩展 `ConversationRepository`：读取摘要、按游标读取消息、读取 Turn 状态、乐观锁保存结构化摘要。
- 扩展 `SessionSummaryRecord`：覆盖游标和 Schema 版本。
- 调整 `CareerResponseRunner`：把已解析的模型连接交给记忆服务，并使用返回的摘要与最近轮次构建 Prompt。
- 扩展 `ResponseGenerationSettings` 和 `config/career_assistant.yaml`：四个记忆预算参数。
- 扩展 `OpenAICompatibleChatClient.complete_json()` 的可选 operation 元数据，默认值保持现有岗位分析行为，记忆调用使用独立 Trace 名称和标签。
- 新增 Alembic 迁移扩展 `session_summaries`，不创建新的记忆表。
- 更新求职助手模块文档，记录目标、调用链、配置、失败降级和暂不支持的边界。

## 验证标准

后端单元与集成测试至少覆盖：

1. 当前轮用户消息不会被重复放进历史；
2. 最近历史只包含完整用户—助手轮次；
3. 短对话不触发摘要模型；
4. 超过阈值时只压缩最旧完整前缀并保留最近目标轮数；
5. 摘要 JSON 严格区分用户事实和助手建议；
6. 摘要成功后覆盖游标落在助手消息上；
7. 非法 JSON、超长摘要和模型错误均不推进游标；
8. 两个并发压缩结果只有一个能通过乐观锁；
9. 已有摘要与最近原文合计不超过历史 Token 预算；
10. 单轮超长时不留下孤立 user 或 assistant 消息；
11. 简历、JD 和当前用户纠正的优先级高于滚动摘要；
12. 结构版本不匹配或无覆盖游标的旧摘要不被注入；
13. 流式和非流式回复使用同一记忆组装逻辑；
14. 记忆组件失败时原有回复仍能成功完成。

增加 100 轮和 300 轮确定性模拟对话：在前 10 轮给出目标，在中段修改目标，在末段追问；断言最终 Prompt 包含新目标、排除旧目标，并保持预算不越界。测试不要求调用真实 Provider，摘要模型使用可控 Fake。

最后运行相关 Python 测试、完整后端测试和项目现有静态检查。该功能不改变页面结构，因此不新增前端视觉验收；历史消息页面仍展示完整原始记录。

## 后续边界

上线后先观察摘要触发次数、失败率、Prompt 历史 Token、用户纠正保留率和长对话回忆测试结果。只有出现可复现的“滚动摘要知道主题但丢失具体旧细节”，才设计分段摘要和混合召回。只有产品明确要求新会话继承自由事实，才单独设计带来源、作用域和纠错链的跨会话记忆；两者都不属于本次实施。
