# 面试大师逐句触发与连续追问设计

## 1. 目标

优化浏览器端“面试大师”的问题触发逻辑，使面试官每次产生完整 `final` 转写后都能自动进入回答流程，覆盖显式问句、无问号问句、陈述式任务和祈使式任务；同时把追问上下文从前面 2 条转写扩大到前面 4 条，支持连续三四轮追问。

本次沿用现有页面、“本场问答”、问题类型和短期记忆结构。只调整自动触发、自动回答调度和追问上下文截取，不引入 LLM 意图分类、长期摘要或新的持久化结构。

## 2. 已确认的产品决策

1. 所有 `interviewer + final` 转写均视为自动回答候选，不再要求包含问号、疑问词或固定请求词。
2. 精确过滤纯填充词，例如“嗯”“哦”“好的”“行”；过滤相邻短时间内的完全重复转写。
3. `candidate` 转写和任何 `partial` 转写不得触发答案。
4. 自动问题按到达顺序进入 FIFO 队列。新问题不得取消正在生成的旧问题。
5. 追问仍沿用现有 `FOLLOW_UP` 分类规则，不重做记忆架构。
6. 追问请求携带前面最近 4 条转写，当前问题继续通过独立字段传入，因此总计最多包含 5 条相关话语。
7. 候选人麦克风转写继续遵守现有边界：开启后可进入当前连接的短期上下文，但浏览器端不持久化，也不进入“本场问答”。
8. 前端页面结构和“本场问答”交互不变。

## 3. 非目标

- 不新增 LLM 意图识别或二次分类调用。
- 不建立全场摘要、向量记忆或新的 Token 压缩策略。
- 不把简历、岗位、面经或候选人资料接入实时回答。
- 不修改 ASR Provider、VAD 静音阈值或音频采集链路。
- 不新增数据库表、字段或迁移。
- 不进行手机端、平板端或前端视觉改版。
- 不改变生产环境；实现与验证默认仅在本地进行。

## 4. 当前问题

当前 `RuleBasedQuestionDetector` 先检查问号和固定关键词。`“分析一下日股。”`、`“评价一下这个方案。”` 等需要回答的陈述式任务会在入口被丢弃。与此同时，`“我没什么问题了。”` 可能因为包含“什么”而误触发。

检测成功后，`LiveSessionManager` 会取消正在生成的答案并立刻切换到新问题。扩大触发范围后，如果继续沿用这一状态机，连续到达的两个 `final` 会导致前一条答案被取消，无法满足“每条问题都回答并进入本场问答”。

当前追问 Prompt 只取 `recent_conversation[-2:]`。由于当前问题已经在生成前写入该列表，最近两条中包含当前问题本身，实际只带入一条更早的历史，而且当前问题会重复出现。

## 5. 触发策略

### 5.1 基本门禁

检测器只保留以下确定性门禁：

1. `event.role` 必须为 `INTERVIEWER`。
2. `event.is_final` 必须为 `True`。
3. 规范化文本不能为空。
4. 规范化后不得精确命中纯填充词集合。
5. 不得命中短时间重复保护。

通过门禁后必须返回 `DetectedQuestion`。问号、疑问词和祈使词不再参与“是否触发”的判断。

### 5.2 文本规范化

- 把连续空白压缩为单个空格并去除首尾空白。
- 填充词比较时额外去除首尾常见中英文标点并执行大小写折叠。
- 填充词只做整句精确匹配，不能做子串匹配。例如“好的”应忽略，但“好的，请继续说明缓存一致性”必须触发。

首版填充词集合保持克制，覆盖明确无作答价值的短语：

```text
嗯、嗯嗯、哦、噢、啊、好的、好、行、可以、知道了、明白了、okay、ok
```

不得因为文本长度短而直接忽略，以免漏掉“为什么”“展开”“继续”等有效问题或任务。

### 5.3 完全重复保护

- 只比较规范化后的完整文本，不做编辑距离或语义相似度判断。
- 同一连接内，相同面试官文本在 3 秒内再次成为 `final` 时忽略第二次触发。
- 超过 3 秒后允许相同文本再次触发，支持面试官主动重复问题。
- 重复保护只影响自动回答，不影响转写展示与原有持久化。

### 5.4 问题类型

现有 `_classify` 和追问标记继续使用，但职责降级为“选择回答方式”，不再决定是否生成答案：

- 命中追问标记且存在前一个已检测问题时，类型为 `FOLLOW_UP`。
- 其他文本继续映射到项目、系统设计、算法、场景、行为或知识类。
- `question.detected` 事件合同保持不变。所有通过确定性门禁的自动问题统一使用 `confidence=1.0`；该字段表示“已通过产品触发规则”，不表示语义问题概率，也不得再作为触发门槛。

为避免快速到达的第二个问题因第一个问题尚未开始生成而丢失追问关系，检测器使用“最近已接受的问题”，而不是仅使用“当前正在生成的问题”作为前序问题。

## 6. FIFO 回答队列

### 6.1 队列项

每个自动触发结果形成一个不可变队列项，至少包含：

```text
检测结果 DetectedQuestion
入队时捕获的前面最近 4 条转写
来源：automatic
```

历史快照必须在该问题入队时捕获，不能在真正开始生成时再读取共享列表。否则后续已经到达的问题可能错误进入更早问题的 Prompt。

### 6.2 调度规则

1. 新自动问题只入队，不取消当前答案。
2. 会话内只有一个自动回答 worker，按 FIFO 顺序取出队列项。
3. 队列项开始处理时才递增 `question_version` 并发送 `question.detected`。
4. 随后沿用现有 `answer.started → answer.delta → answer.completed` 事件顺序。
5. 当前答案完成或失败后，worker 自动处理下一项。
6. 单题生成失败不得终止队列；前端继续收到原有错误事件，下一题仍可开始。
7. 会话结束或连接关闭时取消当前 worker 并清空未处理队列，不增加跨连接恢复机制。

延后发送 `question.detected` 可以保持现有单活动问题的前端状态模型。左侧实时转写仍会立即显示新 `final`，但右侧“当前问题”只展示正在处理的队列项。

### 6.3 手动控制

- “重新生成”继续针对当前活动问题，沿用现有 attempt 语义，不改变后续自动队列顺序。
- “立即回答”继续作为显式用户覆盖：取消当前生成，把该活动问题视为用户主动放弃且不重新入队；立即处理手动问题，完成后继续原有待处理自动队列。这是用户主动控制，不属于自动问题互相取消。
- 手动问题与当前活动问题或待处理队列项完全相同时，不重复加入自动队列。
- 暂停和结束继续沿用现有资源清理路径。

## 7. 追问上下文

### 7.1 快照时机

处理一个面试官 `final` 时，先从 `_recent_conversation` 捕获前面最近 4 条，再把当前 `final` 写入短期列表。这样队列项天然得到“不包含当前问题”的历史快照。

候选人 `final` 仍只写入短期列表，不创建回答队列项。浏览器端候选人转写继续由现有 persistence hook 排除持久化。

### 7.2 Prompt 规则

- 非 `FOLLOW_UP`：保持现有规则，只根据当前问题回答，不附带历史。
- `FOLLOW_UP`：把队列项中的前面最多 4 条转写作为指代理解上下文，再单独传入当前问题。
- 历史只用于理解“它、刚才、这个方案、那一致性呢”等指代，不得据此编造个人事实。
- 不把模型上一轮生成的答案加入记忆，不新增摘要或长期对话对象。

## 8. 数据流

```text
ASR event
  → TranscriptAssembler 接受 final
  → 捕获当前 final 之前的最近 4 条转写
  → 写入实时转写列表与现有 persistence hook
  → interviewer final 进入确定性门禁
      → 填充词 / 3 秒内完全重复：只展示转写，不入队
      → 其他文本：分类并创建队列项
  → 单 worker 按 FIFO 取队列项
  → question.detected
  → 组装当前问题和可选的 4 条追问历史
  → 流式生成答案
  → answer.completed
  → 现有“本场问答”追加记录
  → 继续处理下一队列项
```

## 9. 接口与持久化兼容性

- `TranscriptEvent`、`DetectedQuestion`、`QuestionIntent` 和 WebSocket 事件名称不变。
- 前端继续按单个活动 `question_version` 消费流式事件。
- `live_interview_utterances` 和 `live_interview_answers` 表结构不变。
- 浏览器候选人转写仍不持久化。
- 自动问题只有开始生成后才写入 answer 记录；未开始的内存队列项不会跨断线恢复。

## 10. 错误处理与边界

- ASR `partial`、候选人转写、空白文本不触发答案。
- 填充词和重复文本只被跳过自动回答，仍可展示为实时转写。
- 模型生成失败时保留失败事件并继续下一队列项。
- 迟到的旧答案增量继续由现有 `question_version` 和 `attempt` 校验丢弃。
- 自动回答队列只存在于当前连接内存；考虑到已确认的低提问频率，首版不另设持久化补偿、跨连接恢复或独立限流策略。
- 显式用户取消、暂停或结束具有高于自动队列的优先级。

## 11. 测试设计

### 11.1 检测器单元测试

- 显式问句触发：`“Redis 为什么这么快？”`
- 无问号问句触发：`“Redis 为什么这么快”`
- 陈述式任务触发：`“分析一下日股。”`
- 祈使式任务触发：`“评价一下这个方案。”`
- 短有效任务触发：`“展开。”`
- 面试官填充词不触发：`“嗯。”`、`“好的。”`
- 含填充词前缀的完整任务仍触发：`“好的，请继续说明。”`
- candidate final 不触发。
- interviewer partial 不触发。
- 3 秒内完全重复只触发一次，窗口外允许再次触发。

### 11.2 会话状态机测试

- 两个面试官 final 快速到达时，第一条不被 `superseded` 取消。
- 两条问题按顺序产生两个完整回答并各自进入 answer hook。
- 第一条生成失败后第二条仍开始。
- 队列项开始时才发送对应的 `question.detected`。
- 手动回答和重新生成保持现有 attempt 行为。
- 结束会话后当前生成和待处理队列均停止。

### 11.3 追问上下文测试

- `FOLLOW_UP` Prompt 包含当前问题之前的最近 4 条转写。
- 当前问题只出现于“面试官问题”字段，不在追问历史中重复。
- 队列等待期间到达的后续话语不会进入更早问题的上下文快照。
- 不足 4 条时按实际条数传入。
- 非追问不附带历史。
- 开启候选人通道时，候选人 final 可出现在临时追问上下文，但不触发回答。

### 11.4 前端回归

- 现有 `question.detected`、流式增量和 `answer.completed` reducer 测试继续通过。
- “本场问答”按完成顺序追加两条连续问题。
- 当前问题、立即回答、重新生成、暂停和结束按钮行为不回归。

## 12. 验收标准

1. `“分析一下日股。”`、`“评价一下这个方案。”` 和无标点问题均自动生成答案。
2. `“嗯。”`、`“好的。”` 不生成答案。
3. 两个问题连续到达时均完成回答，不发生自动 `superseded`。
4. 追问 Prompt 包含当前问题之前的最多 4 条转写，且不重复当前问题。
5. 不新增意图识别模型调用，不增加数据库迁移，不修改前端页面结构。
6. 实时面试后端核心与服务测试、相关前端测试及前端生产构建全部通过。
7. 模块文档同步记录设计目标、调用链、技术取舍、验证结果和后续边界。

## 13. 实施边界

首版只实现本设计明确描述的触发、队列和四条追问上下文。不增加语义去重、主题摘要、跨连接队列恢复、候选人文本持久化或新的前端队列界面。所有修改和验证仅在本地完成，未经当次明确授权不得部署生产。
