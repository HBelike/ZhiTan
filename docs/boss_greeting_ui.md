# BOSS 一键打招呼：智能生成与真实串行发送

## 设计目标

PC 端复用现有职位库和求职助手页面，为用户逐条审核后的 1–10 个岗位生成并发送招呼语。本功能通过本地 Chrome 扩展复用用户已登录的 BOSS 页面，不部署平台账号凭证，也不把 Cookie、Token 或聊天记录回传到 WebUI。

核心流程：

```text
在左侧岗位卡直接多选 1–10 个岗位
  → 读取每个岗位的完整 JD
  → DeepSeek 为每岗生成一条招呼语并逐条审核
  → 6–10 条时二次确认账号风险
  → 单条真实发送 → 点击发送后立即处理下一条
```

## 页面与交互

- 选岗：复用 `JobSearchWorkspace`，岗位卡左侧提供直接多选框；点击卡片正文仍只预览详情，不再要求先预览再点击右侧“加入本批”。用户配置的本批上限保持为 1–10。
- 详情补齐：搜索返回岗位摘要后，以最多 2 路并发在后台预取当前页完整 JD；岗位预览、勾选和后台预取共用同一请求与缓存。勾选立即生效，不再等待详情；只有进入生成阶段前必须等待本批完整 JD 就绪。单个岗位加载失败只在该卡片提示，取消勾选或重新搜索会使迟到结果失效；登录、验证、限流或会话刷新失败会停止继续预取。
- 审核：左侧固定发送顺序；中间只编辑当前岗位的一条招呼语；右侧把简历证据和岗位关注点拆成上下两个等高分区，两类依据始终同时可见。每个分区固定标题和条目数量，长列表在分区内部独立滚动；空数据展示明确空状态，不改变生成接口或证据数据结构。
- 单条操作：支持直接编辑、取消本批发送、只重新生成当前一条。重新生成会把上一版文案作为避重复参照，但不会把它当成事实来源。
- 文案：目标 80–150 个中文字符，服务端硬限制为 60–180 个字符；从当前简历与完整 JD 选择 1–3 个最相关证据，自适应组织为自然开场，不使用固定句式拼接。
- 生成状态：每个岗位独立显示“生成中、可审核、失败”；最多并发生成 3 条。单条失败不阻塞其他岗位，失败且没有文案的项目不能进入真实发送队列。
- 默认招呼语：无需关闭；若 BOSS 自动发送默认招呼语，定制文案作为下一条消息继续发送。
- 风险：最终发送数量为 6–10 时，必须再次确认限流、安全验证、额度限制及封禁风险。
- 进度：展示“正在发送、已触发发送、已跳过、发送失败、已停止”，始终提供“停止剩余发送”。
- 安全预览：`greeting-preview.html` 显式启用 `simulationMode`，只演示 UI 状态，不调用扩展发送动作。

## 智能生成调用链

```text
CareerGreetingDialog
  → POST /api/career/greetings/generate
  → CareerGreetingService
  → 按当前用户读取候选人简历 + 校验完整 JD
  → 精确选择 READY 的 deepseek / deepseek-v4-pro 文本档案
  → DeepSeek Chat Completions JSON Output
       temperature=0.2, max_tokens=800, thinking=false
  → 校验字数、证据编号、高价值学历/学术成果、个人成果链接、数字/英文标识与上一版相似度
  → 不合格时携带校验错误纠正一次
  → 返回文案、证据摘要、JD 关注点与模型元数据
```

- 模型固定为 `deepseek-v4-pro`，不跟随聊天页模型选择器，也不降级到其他模型。没有可用档案或 API Key 时明确提示用户配置，避免静默生成模板文案。
- 复用现有 OpenAI-compatible Chat Completions 客户端；JSON Output 是本次调用协议，模型档案保持 `TEXT` 能力即可。
- 浏览器只收到生成后的证据摘要，不返回完整简历、完整 JD、原始模型响应或 API Key。
- 生成与真实发送相互隔离：生成可以最多 3 路并发，扩展发送仍严格单条串行。

## 真实发送调用链

```text
CareerGreetingDialog
  → jobLibraryBridge.sendGreeting（单岗位、单文案）
  → 扩展检查登录、验证、岗位详情和聊天标识
  → 单次 friend/add
  → BOSS 官方聊天页填入文案并单次点击“发送”
  → 点击动作完成后立即返回 submitted
  → WebUI 直接启动下一岗位，不等待送达或成功回执
```

- WebUI 持有批次队列，扩展每次只接受一个岗位，避免扩展脱离页面继续批量执行。
- 发送使用 BOSS 正常网页聊天路径，不实现私有 WebSocket 协议。
- 搜索、详情和发送前预检遇到会话状态失效时，自动刷新 BOSS 标签页一次并重试只读请求；不依赖后台定时器或跨操作冷却。
- `friend/add` 和“发送”点击均不自动重试。扩展只确认输入框写入成功、发送按钮可用且点击动作已执行，不再监听聊天 DOM 的送达、成功或失败状态。
- 单岗在点击前遇到岗位失效、此前已沟通、登录失效、验证码、限流、DOM 异常或标签页异常时，记录为跳过或失败，但不会停止后续岗位；后续岗位仍按顺序各执行一次发送尝试。
- 用户点击“停止剩余发送”是唯一会终止后续队列的条件；当前已触发点击的项目记录为“已触发发送”，不再把 BOSS 回执当作批次推进条件。
- 继续保持单标签页、单岗位串行，避免并行导航覆盖文案，并降低集中并发触发带来的账号限制风险。

## Prompt 与证据边界

当前实际 System Prompt 位于 `src/career_assistant/greetings.py` 的 `_SYSTEM_PROMPT`，设计与校验规则定义在：

- `docs/superpowers/specs/2026-08-25-smart-boss-greeting-generation-design.md`

服务端把简历和 JD 分别编号为 `CV-xxx`、`JD-xxx`。模型必须先选择真实存在的证据，再生成单段开场白并返回 JSON；不能把岗位要求写成求职者已经具备的经历，也不能补写未出现的数字、公司、学校、技能或项目结果。程序会确定性检出简历中明确写出的 `985/211/双一流/QS`、博士/硕士、论文/专利等高价值优势类别，并要求每个已出现类别在文案中至少表达一项且引用对应 `CV-xxx`；没有证据时不会根据校名或模型常识补全。

个人网站、作品集、项目地址以及 GitHub/GitLab/Gitee、PR/开源贡献记录属于可验证成果链接。简历存在此类 URL 时，Prompt 要求模型原样附上至少一个，服务端同时验证 URL 来自简历且对应证据编号已被引用；遗漏、改写或无证据的链接会进入既有的一次纠正流程。

“去模板化”和 humanizer 原则已经合并进同一次 System Prompt：根据证据组合自适应选择切入点、句式和礼貌问询，避免“我非常符合贵司要求”“期待您的回复”等套话。运行时不依赖 Codex Skill，也不执行一个可能改写事实的第二阶段模型调用；事实准确性最终由服务端确定性校验兜底。

## 本地使用

1. 在 `chrome://extensions` 开启开发者模式，加载或重新加载 `browser-extension/job-library`。
2. 保持一个已登录且无验证码拦截的 BOSS 页面。
3. 启动 WebUI，在求职助手中进入“一键打招呼”，选岗、审核文案并确认真实发送。
4. 仅验证 UI 时访问 `http://127.0.0.1:5173/greeting-preview.html`；该页面永远不会发送到 BOSS。

真实账号验收会产生对外沟通，应由用户在最终岗位与文案可见时主动点击确认；本地自动验证不代替用户执行真人账号发送。
