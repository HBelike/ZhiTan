# PRD：基于基准简历与目标岗位的求职助手上下文工作台

> 文档状态：产品决策已确认 / PC 端交互第一版已实现
> 版本：v0.2
> 日期：2026-08-20
> 产品范围：PC 端求职助手改造；PC 验收后再单独设计手机端
> 2026-08-21 修订决策：开启对话不再依赖简历或目标岗位；两项资料分别可选，并可在会话中增量补充。本文后续保留的“强制确认”描述仅代表首版方案，均以本修订为准。

## 2026-08-21 流程修订

1. 新会话与未绑定资料的历史会话均可直接发送消息。
2. 基准简历和目标岗位独立可选，不要求成对上传或确认。
3. 用户后续补充任一资料时，为当前会话创建新的上下文绑定版本；未提交的一项沿用当前版本。
4. 模型只注入实际存在的资料：无资料时执行通用求职咨询，单项资料时执行对应范围的分析，两项齐全时才生成岗位匹配结论与四维画像。
5. 历史消息不因资料更新而重写；后续 Turn 使用最新绑定。

## 1. Summary

当前求职助手把简历、职位链接和岗位材料当作“某一轮聊天的临时输入”，允许用户先创建空会话或只输入普通问题。这与目标产品不符：求职建议无法持续基于同一份候选人事实和同一目标岗位，跨轮对话也没有稳定的数据基础，因此技能匹配度、经验匹配度等指标无法真实、可复算地成立。

本次改造将求职助手调整为“先建立求职上下文，再开始对话”：

1. 用户先选择或上传一份基准简历，系统解析为可确认、可版本化的 `CandidateProfileContext`。
2. 用户通过文本域、文件或职位 URL 配置目标岗位，系统解析为可确认、可版本化的 `TargetRoleContext`。
3. 两份上下文确认后，系统生成证据化的匹配画像，才允许创建会话并调用大模型。
4. 会话中自动把基准简历、目标岗位、当前问题以及按需检索的面经证据组合为模型输入。
5. 页面持续展示可解释的岗位匹配指标；每个分数均可下钻到“岗位要求—简历证据—计算状态”，不展示无证据的主观总分。

产品语义上可以理解为“两份系统上下文”：候选人角色信息和目标岗位信息。技术实现上不把简历或 JD 直接作为两个可以覆盖平台规则的最高优先级 `system` 消息，而采用“一条平台系统规则 + 两个有类型、有版本、有来源的结构化上下文块”，避免简历/JD 中的文本影响系统指令优先级。

### 1.1 一句话价值

让用户得到的每次求职问答，都能回答“这条建议基于我的哪段经历、目标岗位的哪项要求、参考了哪份面经”。

### 1.2 本期非目标

- 不在 V1 生成一个无法解释的“综合匹配度 83 分”。
- 不在 V1 自动替用户投递职位、修改外部招聘平台资料或采集登录态页面。
- 不把面经内容当作岗位官方要求或候选人真实经历。
- 不进行手机端专项适配；PC 端交互和数据链路验收后再安排。
- 不重做现有模型连接、附件解析、面经入库和 Skill 挂载能力，只调整它们在求职助手中的编排位置。

## 3. Background

### 3.1 用户任务

用户不是在使用一个通用聊天机器人，而是在持续完成同一个求职任务：

> “请以我的真实经历为边界，以当前目标岗位为目标，结合可靠面经资料，帮助我判断差距、准备表达并应对面试。”

要完成这个任务，简历和岗位都不是可选附件，而是会话成立的先决条件。

### 3.2 当前实现与目标体验的差距

| 边界 | 当前实现证据 | 目标体验 | 缺口结论 |
|---|---|---|---|
| 新建会话 | `CareerAssistantPage.vue:1302-1304` 点击后直接创建会话 | 点击“开启新对话”先进入上下文配置 | 入口顺序相反 |
| 空会话提示 | `CareerAssistantPage.vue:1390` 明确允许先聊、需要时再上传材料 | 未确认简历和岗位前不能进入正式聊天 | 产品规则相反 |
| 发送前校验 | 文本输入与可用模型就绪即可发送 | 简历、目标岗位分别作为可选增强上下文 | 不再设置资料门禁 |
| 简历生命周期 | `CareerAssistantPage.vue:758` 每轮作为 `resume_file` 提交；`router.py:886` 声明原文件临时接收；`intake_graph.py:38-42` 原始上下文只在当前 Graph 内存中存在 | 解析结果形成可复用、可确认、可版本化的候选人上下文 | 仅单轮临时材料，不是 baseinfo |
| 岗位生命周期 | `contracts.py:187` 只有本轮 `job_url`；`response_runner.py:583-587` 只在本轮拼接职位页面文本 | 一份目标岗位上下文绑定整个会话，修改产生新版本 | 没有会话级岗位对象 |
| Prompt 语义 | `response_runner.py:473-615` 基础 system + 历史 + 本轮附件/JD/面经 | 平台规则 + 候选人上下文 + 目标岗位上下文 + 按需证据 + 当前问题 | 缺少稳定的双上下文层 |
| 面经 RAG | 已支持 `@面经`，服务端按本轮问题取最多 6 个片段并保留引用 | 根据目标公司、岗位和问题自动缩小检索域，同时保留显式选择 | 已有能力可复用，但联动不足 |
| 匹配指标 | 页面没有会话级匹配数据；系统规则还要求材料不足时不虚构分数 | 指标必须依赖确认后的岗位要求和简历证据，并可复算、可下钻 | 缺少数据模型与计算契约 |

### 3.3 外部成熟模式的可复用结论

- ChatGPT Projects 将聊天、文件和项目指令组合为持续上下文，聊天进入项目后继承文件和指令。这验证了“先建立上下文容器，再开展多轮对话”的产品模型。[OpenAI Projects 官方说明](https://help.openai.com/en/articles/10169521-using-projects-in-chatgpt-496)
- Claude Projects 把项目知识和项目指令用于项目内聊天，并在知识量增大时使用 RAG。这验证了“稳定资料 + 会话 + 按需检索”应当是同一条产品链路。[Anthropic Projects 官方说明](https://support.anthropic.com/en/articles/9517075-what-are-projects)
- Langfuse 将一次聊天轮次视为 trace、完整会话视为 session，并把质量分数挂到 trace、observation 或 session。这支持本 PRD 将“会话级匹配画像”和“单轮回答级证据指标”分开。[Langfuse Trace 最佳实践](https://langfuse.com/docs/observability/best-practices)、[Langfuse Score 模型](https://langfuse.com/docs/evaluation/scores/overview)

上述模式只提供结构参考。本产品的简历事实约束、岗位要求拆解和面经来源边界需要独立定义。

## 4. Objective

### 4.1 产品目标

建立一个有明确数据依赖的求职对话入口，使每个正式会话都绑定已确认的基准简历版本和目标岗位版本，并让岗位匹配指标与回答引用均可追溯。

### 4.2 SMART Key Results

| KR | V1 验收目标 | 数据来源 |
|---|---:|---|
| 上下文生效率 | 已补充资料的会话，后续 Turn 100% 使用最新绑定版本 | `conversation_context_bindings` 与 Turn Trace |
| 指标可解释率 | 100% 的可见匹配分数能展开分子、分母、岗位要求和简历证据 | `match_dimension_scores` + `evidence_links` |
| 个人事实有据率 | 自动回归集中，回答涉及用户经历的关键陈述 100% 可映射到基准简历证据或明确标记“待用户确认” | 回答 claim 与简历 evidence 映射 |
| 面经引用完整率 | 使用面经信息的回答，100% 保留至少一个有效面经来源 ID 和可见引用 | retrieval trace + answer citations |
| 上下文版本一致率 | 100% 的 Turn 可还原其实际使用的简历版本、岗位版本、Prompt 版本和面经检索结果 | Turn context snapshot |
| 启动任务完成时间 | 可用文件情况下，80% 用户在 3 分钟内完成解析、确认并开始对话 | 前端事件漏斗；阈值上线后复核 |

### 4.3 成功判断

V1 成功不以“模型看起来更聪明”为标准，而以以下事实为标准：同一个问题在同一组上下文版本上可复现输入边界；指标有证据和公式；上下文变化不会悄悄改写旧对话；面经建议带来源。

## 5. Market Segments

### 5.1 有明确 JD 的在职求职者

- Job：判断自己的经历与具体岗位差距，并准备有针对性的面试表达。
- 痛点：通用建议多、与简历无关；每轮重复解释背景；“匹配度”没有依据。
- 核心价值：一次配置，后续所有问题都基于同一份事实与岗位要求。

### 5.2 应届生 / 转岗候选人

- Job：识别技能和项目证据缺口，知道哪些内容可以说、哪些不能硬凑。
- 痛点：经历较少，模型容易把课程、项目和工作经验混为一谈。
- 核心价值：指标区分“直接证据、相邻证据、缺少证据”，不把潜力伪装成已具备经验。

### 5.3 面试准备中的候选人

- Job：结合目标公司和岗位的真实面经，预测高频方向、组织回答和追问。
- 痛点：面经库与个人简历割裂；即使检索到题目，也不知道该用自己的哪段经历作答。
- 核心价值：面经负责“别人被问过什么”，简历负责“我能真实回答什么”，JD 负责“岗位为什么关心”。

## 6. Value Propositions

| 用户问题 | 产品能力 | 用户可见结果 |
|---|---|---|
| 每轮都要重复介绍自己 | 基准简历作为会话级角色上下文 | 顶部持续显示当前简历版本 |
| 不知道建议是否针对当前岗位 | 目标岗位作为会话级目标上下文 | 每条建议可关联岗位要求 |
| “匹配度”像模型拍脑袋 | 确定公式 + 要求项权重 + 简历证据映射 | 分数可展开、可复算 |
| 面经库和聊天割裂 | 公司/岗位过滤 + 问题级 RAG | 回答保留面经来源并与个人经历结合 |
| 修改 JD 后上下文混乱 | 上下文版本与 Turn 快照 | 旧回答保持原版本，新回答使用新版本 |
| 模型容易补写经历 | 基准简历事实边界 + claim grounding | 无证据内容明确标为建议或待确认 |

## 7. Solution

### 7.1 核心用户流程

```text
点击“开启新对话”
  → Step 1：选择/上传基准简历
      → 解析文件
      → 展示结构化事实与解析警告
      → 用户编辑并确认 CandidateProfileContext vN
  → Step 2：配置目标岗位
      → 粘贴 JD / 上传文件 / 输入职位 URL
      → 解析岗位要求、must/preferred、职责和年限
      → 用户编辑并确认 TargetRoleContext vN
  → Step 3：确认求职上下文
      → 可选：选择公司/岗位面经范围
      → 生成首版证据化匹配画像
      → 点击“开始对话”
  → 创建 conversation + context binding
  → 进入对话工作台
      → 每轮按问题检索简历证据、岗位要求和面经片段
      → 调用 LLM
      → 展示回答、引用和单轮指标
```

### 7.2 PC 端页面结构

#### 7.2.1 对话前：上下文启动向导

```text
┌────────────────────────────────────────────────────────────────────┐
│ 开启求职对话                    1 基准简历  2 目标岗位  3 确认      │
├───────────────────────────────┬────────────────────────────────────┤
│ 输入区                         │ 解析与确认区                       │
│                               │                                    │
│ [选择已有简历] [上传文件]      │ 基本事实 / 技能 / 经历 / 项目      │
│ 文件名、解析进度、错误状态      │ 每项显示来源位置与“待确认”状态      │
│                               │                                    │
│                               │ [重新解析] [保存并继续]             │
├───────────────────────────────┴────────────────────────────────────┤
│ 取消                                          下一步（未确认时禁用）│
└────────────────────────────────────────────────────────────────────┘
```

岗位步骤左侧提供三个等价入口：

- 文本域：粘贴完整 JD，适合大多数用户。
- 文件解析：PDF、DOC、DOCX、图片；复用现有 AttachmentParser / Docling / OCR / Vision。
- 职位 URL：保留现有公开页面提取能力；提取失败时不阻塞用户改为粘贴正文。

若同时提供多个来源，系统先合并为一份“规范化岗位正文”，用户确认后的正文才是后续事实来源。文件和 URL 只是导入方式，不直接成为长期 Prompt。

#### 7.2.2 对话中：三栏工作台

```text
┌──────────────┬──────────────────────────────────────┬───────────────┐
│ 会话历史      │ 基准简历 v3 · 目标岗位 v1 · 面经 12  │ 求职匹配画像   │
│              ├──────────────────────────────────────┤ 技能覆盖 86%  │
│              │ 对话与来源引用                       │ 经验证据 80%  │
│              │                                      │ 项目相关 80%  │
│              │                                      │ 关键缺口 10%  │
│              ├──────────────────────────────────────┤ [查看证据]    │
│              │ 输入框 / @面经 / Skill / 模型         │ 本轮引用与状态 │
└──────────────┴──────────────────────────────────────┴───────────────┘
```

顶部上下文条必须显示：

- 基准简历名称、版本、确认时间和“调整简历”入口；
- 目标公司/岗位、版本和“调整岗位”入口；
- 当前面经检索范围；
- 当前模型和 Prompt 版本仅在详情中显示，不干扰普通用户。

### 7.3 按钮和状态定义

| 操作 | 前置条件 | 成功结果 | 失败反馈 |
|---|---|---|---|
| 开启新对话 | 无 | 打开启动向导，不立即创建 conversation | 向导无法加载时显示可重试错误 |
| 解析简历 | 已选择支持的文件 | 展示结构化候选人事实和来源 | 显示具体格式/页数/解析服务错误 |
| 保存基准简历 | 所有必需解析项已确认 | 创建不可变 resume version | 逐字段显示未确认项，不清空用户编辑 |
| 解析岗位 | 文本、文件或 URL 至少一种 | 展示规范化要求清单 | 保留原输入并提供重试/改为粘贴 |
| 开始对话 | 简历版本、岗位版本已确认且模型可用 | 原子创建 conversation 和 context binding | 不创建半成品会话 |
| 调整岗位 | 已在对话中 | 保存为新岗位版本；后续 Turn 使用新版本 | 当前上下文保持不变 |
| 查看证据 | 指标已有计算结果 | 展开要求、权重、匹配状态和简历证据 | 无证据项显示“未找到”，不能补造说明 |

### 7.4 上下文与 Prompt 设计

#### 7.4.1 CandidateProfileContext

只包含用户确认后的求职相关事实：

- 工作经历：公司类型、岗位、起止时间、职责、成果；
- 项目经历：项目目标、职责、技术、成果；
- 技能：标准化技能名、原文别名、熟练度仅在原文明确时保留；
- 教育与证书；
- 求职约束：地点、行业、职级等，由用户显式补充；
- 每条事实的 `source_span`、确认状态和版本。

姓名、手机号、邮箱、身份证号等不是匹配所需事实，不进入模型上下文。

#### 7.4.2 TargetRoleContext

只包含用户确认后的岗位目标：

- 公司、岗位、职级、地点；
- `must_have` 与 `preferred` 要求；
- 技能、年限、领域、职责、教育/证书要求；
- 每条要求的权重、原文片段、用户确认状态；
- 岗位来源和版本。

#### 7.4.3 每轮模型消息顺序

```text
system: 平台角色、事实边界、隐私、引用和工具规则
system: 已激活 Skill（沿用现有边界，仅在用户显式调用或会话继承时出现）
system/context: <candidate_profile version="...">用户确认事实</candidate_profile>
system/context: <target_role version="...">用户确认岗位要求</target_role>
history: 最近对话与受控摘要
context: 本轮检索到的简历证据、岗位要求、面经片段
user: 当前问题
```

如果现有 Chat Completions 协议不支持独立 `context` role，则把两个上下文块放入受平台控制的 `system` 消息中，并明确标记其中内容是数据而非指令。简历、JD、面经和 Skill 参数均不能覆盖首条平台系统规则。

### 7.5 面经库联动

#### 7.5.1 检索条件

每轮面经 RAG 查询由以下字段组成：

```text
当前用户问题
+ TargetRoleContext.company_name
+ TargetRoleContext.role_name
+ TargetRoleContext.skills（仅取与问题相关项）
+ 用户显式选择的 interview_experience_ids（可选）
```

检索优先级：

1. 用户显式 `@面经` 选择的资料范围；
2. 当前目标公司 + 相同/相邻岗位；
3. 相同岗位的跨公司面经；
4. 无足够证据时明确返回“面经库暂未找到可靠参考”，不使用无来源常识冒充面经。

#### 7.5.2 回答规则

- 面经回答必须保留 `[面经：公司 · 岗位 · 标题]` 来源标识和内部 chunk ID。
- 面经只能说明“历史候选人经验中出现过”，不能说明“官方一定会问”。
- 生成 STAR 示例时，只能使用基准简历中的事实；面经题目不能反向写入候选人经历。
- 用户问“我该怎么答”时，模型先取面经题目/考点，再从基准简历检索可用经历，最后根据 JD 解释回答重点。

### 7.6 指标体系

指标分为两层，避免把产品画像和系统评测混为一谈。

#### 7.6.1 用户可见：会话级岗位匹配画像

所有公式使用已确认的 `TargetRoleContext` 要求项。默认权重为 `must_have = 2`、`preferred = 1`；用户修改要求优先级后重新计算。匹配因子统一为：

- `1.0`：基准简历存在直接证据；
- `0.5`：存在可解释的相邻证据或略低于明确阈值，必须展示差异；
- `0.0`：未找到证据或明确不满足；
- `N/A`：岗位未给出该类要求，不参与分母。

| 指标 | 意义 | 计算方式 | 下钻内容 |
|---|---|---|---|
| 技能证据覆盖率 | 简历技能对 JD 技能要求的覆盖 | `Σ(技能要求权重 × 匹配因子) / Σ技能要求权重 × 100%` | 技能要求、must/preferred、简历原文、直接/相邻/缺失 |
| 经验要求达成率 | 年限、领域、职责范围是否有经历证据 | `Σ(经验要求权重 × 匹配因子) / Σ经验要求权重 × 100%` | 年限差、领域证据、职责证据、缺少项 |
| 项目场景适配率 | 简历项目是否覆盖岗位核心工作 | `Σ(岗位职责权重 × 项目证据因子) / Σ岗位职责权重 × 100%` | JD 职责与项目事实的映射 |
| 关键要求缺口率 | must-have 中仍有多少加权缺口 | `Σ[must 权重 × (1 - 匹配因子)] / Σmust 权重 × 100%` | 缺口影响、补证建议；数值越低越好 |

V1 不展示综合总分。原因是技能、经验和项目对不同岗位的真实录用影响权重尚无经标注数据支持；先展示四维画像比人为合成一个百分比更真实。

#### 7.6.2 用户可见：单轮回答证据指标

| 指标 | 意义 | 计算方式 | 展示位置 |
|---|---|---|---|
| 简历事实有据率 | 回答中关于用户个人事实的陈述是否有简历依据 | `有有效 resume evidence 的个人事实 claim 数 / 全部个人事实 claim 数` | 回答下方“依据”抽屉 |
| 面经引用完整率 | 使用面经得出的内容是否带有效引用 | `带有效 citation 的面经 claim 数 / 全部面经 claim 数`；未使用面经时为 N/A | 回答来源区域 |
| 当前上下文版本 | 该回答实际基于哪份简历/JD | 直接读取 Turn snapshot，不计算 | 回答时间旁 |

单轮指标不要求每次都用 LLM 打分。优先采用结构化生成、引用 ID 校验和规则计算；只有“claim 是否由证据支持”这类语义判断才允许使用版本化 evaluator，并保留判断理由。

#### 7.6.3 管理员 / 评测中心指标

这些指标用于判断系统好不好，不直接冒充用户的岗位匹配度：

- 简历事实抽取准确率、岗位要求抽取准确率；
- 技能标准化 Precision / Recall；
- 面经 Retrieval Recall@K、MRR、NDCG@K；
- 回答引用正确率、无依据个人事实率；
- 首响应延迟、总延迟、Token 和成本；
- 按 `resume_context_version`、`target_role_version`、`prompt_version`、`model_id` 分组比较。

### 7.7 实际计算案例

#### 输入

目标岗位要求：

| 要求 | 类型 | 优先级 / 权重 |
|---|---|---:|
| Python | 技能 | must / 2 |
| FastAPI | 技能 | must / 2 |
| PostgreSQL | 技能 | must / 2 |
| RAG | 技能 | preferred / 1 |
| 3 年后端经验 | 经验 | must / 2 |
| 高并发 API 经验 | 经验 | must / 2 |
| 跨团队协作 | 经验 | preferred / 1 |
| API 设计 | 岗位职责 | must / 2 |
| 性能优化 | 岗位职责 | must / 2 |
| RAG 落地 | 岗位职责 | preferred / 1 |

基准简历证据：

- 2.5 年 Python 后端经历；
- 一个 FastAPI + PostgreSQL 项目；
- 明确写有高并发接口优化和跨团队联调；
- 项目中负责 API 设计和性能优化；
- 没有 RAG 项目或生产经验。

#### 输出

1. 技能证据覆盖率：`(2×1 + 2×1 + 2×1 + 1×0) / 7 = 85.7%`。
2. 经验要求达成率：`(2×0.5 + 2×1 + 1×1) / 5 = 80%`。其中“3 年”只达到 2.5 年，因此显示相邻证据，而不是直接算满足。
3. 项目场景适配率：`(2×1 + 2×1 + 1×0) / 5 = 80%`。
4. 关键要求缺口率：must 项中只有“3 年经验”存在 0.5 缺口，`2×(1-0.5) / (技能 must 6 + 经验 must 4 + 职责 must 4) = 7.1%`。

页面不能只显示四个百分比。点击“技能覆盖 85.7%”后必须看见 RAG 为 preferred、权重 1、简历未找到证据；点击“经验覆盖 80%”后必须看见 3 年要求与 2.5 年证据的差异。

当用户接着问“这个岗位的 RAG 会怎么问，我该怎么回答？”：

1. 系统基于目标公司、岗位、RAG 技能和当前问题检索面经片段；
2. 回答引用真实面经题目并标记来源；
3. 因简历没有 RAG 经历，模型不得编造项目，而应建议用户坦诚说明缺口，并用已有 API/数据库项目解释可迁移能力；
4. 该回答的简历事实有据率应为 100%，面经引用完整率应为 100% 或 N/A（若未召回面经）。

### 7.8 数据模型建议

| 对象 | 关键字段 | 说明 |
|---|---|---|
| `candidate_profiles` | id, owner_id, display_name, active_version_id | 用户可管理多份基准简历 |
| `candidate_profile_versions` | id, profile_id, version, parsed_text, structured_facts, source_hash, status, confirmed_at | 不可变；保存确认后的解析文本和事实，不保存临时原文件 |
| `target_roles` | id, owner_id, display_name, active_version_id | 可复用的目标岗位 |
| `target_role_versions` | id, target_role_id, version, canonical_text, requirements, source_metadata, status, confirmed_at | must/preferred 与权重均版本化 |
| `conversation_context_bindings` | conversation_id, candidate_version_id, initial_target_version_id, created_at | 会话创建时的基础绑定 |
| `turn_context_snapshots` | turn_id, candidate_version_id, target_version_id, prompt_version, model_profile_id, retrieval_snapshot_id | 还原每轮真实输入边界 |
| `match_assessments` | id, candidate_version_id, target_version_id, algorithm_version, created_at | 同一版本组合可复用计算结果 |
| `match_dimension_scores` | assessment_id, metric_key, numerator, denominator, score, direction | 保存分子分母，不只保存百分比 |
| `match_evidence_links` | assessment_id, requirement_id, resume_fact_id, factor, reason_code | 指标下钻的事实依据 |

上下文版本一旦被 Turn 使用就不可更新。用户修改简历或 JD 时创建新版本；旧消息仍显示原版本，新消息使用新版本。

### 7.10 后端调用链

```text
简历/岗位导入
  → TemporaryAttachmentStore
  → AttachmentParser / JobPostingExtractor
  → ResumeNormalizer / TargetRoleNormalizer
  → 用户确认
  → 持久化不可变 context version
  → MatchAssessmentService（要求—证据映射与确定公式）

开始对话
  → 原子创建 Conversation + ContextBinding

每轮提问
  → 读取 Turn 对应的 candidate/target 版本
  → 检索与问题相关的简历事实和岗位要求
  → InterviewRetrievalService 按目标公司/岗位/问题检索
  → PromptAssembler 组装平台规则、双上下文和证据
  → CareerResponseRunner / 模型 Agent Loop
  → ClaimCitationValidator
  → 持久化回答、Turn snapshot、引用和可观测数据
```

### 7.11 复用与改造边界

#### 可直接复用

- `TemporaryAttachmentStore` 和 `AttachmentParser`：文件接收、Docling、OCR、Vision、临时清理；
- `ResumeNormalizer`：作为确定性初步章节归类器；
- 简历助手现有“简历 + 岗位 → 结构化建议”经验，但不能直接复用其不可更新历史表作为 baseinfo；
- `InterviewRetrievalService`、RRF 和面经 citation；
- 模型连接、SSE 进度、CareerResponseRunner、Skill 挂载和 LangSmith 隐私边界。

#### 必须新增或重构

- 候选人和目标岗位的持久化版本模型；
- 创建会话前的强制上下文校验；
- 单轮临时材料 Prompt 改为版本化上下文 Prompt；
- 要求—证据映射和可复算指标；
- 对话右侧指标面板、证据抽屉和上下文切换提示；
- 面经检索自动加入公司/岗位过滤条件；
- Turn 级 context / retrieval / prompt 快照。

### 7.12 动态修改规则

- 用户可以在会话中动态调整岗位信息，但保存时必须创建 `TargetRoleContext vN+1`。
- 保存后在消息流插入不可删除的系统分隔条：“目标岗位已从 v1 调整为 v2，以下回答基于 v2”。
- 默认不重算、重写或覆盖旧回答；用户可另行发起“基于新岗位重新分析本会话”的显式任务。
- 基准简历也采用相同版本原则。若修改内容较大，页面推荐开启新会话，但不强制。
- 匹配画像随上下文版本组合重新计算，并保留旧 assessment 供历史回答查看。

### 7.13 关键假设与风险

| 风险 / 假设 | 影响 | 处理方式 |
|---|---|---|
| 文件解析不等于事实正确 | 错误事实会污染后续所有轮次 | 资料写入上下文前必须经过预览和用户确认；未确认不影响普通聊天 |
| 技能别名映射可能误判 | 匹配分数失真 | 保留原词、标准词和映射 reason；支持用户修正 |
| 年限和职责难完全规则化 | 可能需要语义判断 | 规则优先，LLM 只生成候选映射；关键项可人工确认 |
| JD 本身不完整 | 某些指标没有分母 | 显示 N/A，不用通用模板补造岗位要求 |
| 面经存在过时或个例偏差 | 用户误以为一定会考 | 强制经验来源提示和日期；不表述为官方事实 |
| 上下文过长 | 成本、延迟、注意力下降 | 保存完整版本，但每轮只检索相关事实；不得每轮塞入全文 |
| “匹配度”被理解为录用概率 | 误导用户 | 命名为覆盖度/证据度/缺口率，不声称预测录用结果 |

### 7.14 验收场景

1. **无资料直聊**：Given 用户点击开启新对话或打开无绑定的历史会话，When 未提供简历和 JD，Then 输入框与发送按钮仍可使用。
2. **单项增量上下文**：Given 会话正在进行，When 用户只补充简历或只补充 JD，Then 保存成功且后续 Turn 只注入该项资料。
3. **匹配画像门槛**：Given 会话只有一项资料，Then 不生成匹配画像；When 两项资料均存在，Then 生成可复核的四维画像。
4. **解析可修正**：Given 解析把 “Fast API” 错映射，When 用户修改为 FastAPI 并确认，Then 后续上下文和指标使用修正值。
5. **版本可追溯**：Given 会话前两轮使用 JD v1，When 用户保存 JD v2 并再提问，Then 第三轮绑定 v2，前两轮仍显示 v1。
6. **分数可复算**：Given 4 个技能要求及其权重/匹配因子，When 打开指标详情，Then 页面分子分母与后端结果一致。
7. **无要求则 N/A**：Given JD 未提出教育要求，When 生成画像，Then 教育维度不参与任何分母，不显示 0 分。
8. **面经有源**：Given 回答使用 2 个面经片段，When 展开来源，Then 能看到公司、岗位、标题、日期和 chunk citation。
9. **不编经历**：Given 简历无 RAG 项目，When 用户询问 RAG 面试回答，Then 模型不得声称用户做过 RAG，仅能说明可迁移能力或建议补充真实材料。
10. **上下文变更失败**：Given 用户编辑 JD v2，When 保存失败，Then 会话仍绑定 v1，草稿不丢失。
11. **空会话创建原子性**：Given 用户未提供资料，When conversation 创建成功，Then 不创建 binding；When conversation 创建失败，Then 不产生任何会话或资料绑定。

## 9. 已确认的产品决策

2026-08-20 已确认采用以下方案：

1. 一个会话同一时刻只绑定一份基准简历版本和一份目标岗位版本。
2. 用户可以保存多份基准简历；新会话默认选择最近使用版本，但仍需确认。
3. 岗位修改保留在同一会话中并产生新版本，不自动重写历史消息。
4. V1 不提供综合匹配总分，只提供四维可解释画像。
5. 面经 RAG 默认自动检索目标公司/岗位范围，`@面经` 作为用户显式限定或补充。
6. 原始上传文件仍按临时材料清理；长期保存用户确认后的解析文本、结构化事实、来源哈希和版本。

- 设计目标：将截图红框区域改为常驻的“目标岗位与匹配画像”侧栏，让用户在对话中持续看到当前 JD，而不是把岗位材料塞在输入框里。

- 数据依赖：新增 Alembic `20260820_14`，保存确认后的简历提纲、目标岗位正文、要求项和会话绑定版本；原始上传文件仍在解析后清理。
