# PC 多屏幕响应式布局系统

## 设计目标

- 消除页面依赖浏览器 `Ctrl + -` 才能完整显示的问题。
- 支持 Chrome、Edge 最新两个大版本，在浏览器 100%、125%、150%、200% 缩放下完成核心操作。
- 覆盖宽屏、标准 PC、Windows 高显示缩放与短屏场景；自动化最低验收边界为 `900 × 420` CSS viewport。
- PC 端先完成并验收；手机端保持已有能力不回退，后续单独适配，不做 iPad 或平板专项设计。
- 保持现有 Vue、Element Plus、路由结构和双主题视觉，不迁移 UI 框架，不重做业务功能。

## 问题根因

当前故障不是显示器物理分辨率不足，而是页面尺寸约束与浏览器 CSS viewport 不匹配：

1. `body` 强制 `min-width: 1280px`，同时使用 `overflow: hidden`，不足 1280px 时内容被裁切。
2. 全局壳层只有完整桌面与 900px 以下移动布局，缺少紧凑 PC 档，形成 901–1279px 兼容性死区。
3. 业务组件使用 viewport media query 和 `100vw` 计算内部布局，没有扣除侧栏及页面内边距。
4. 求职助手、岗位检索、简历助手等页面包含固定栏宽、固定最小宽度或缺少响应式规则。
5. 多层 `100vh`、固定最小高度和 `overflow: hidden` 叠加，导致短屏内容无法滚动访问。
6. 现有测试偏重 DOM 文本与静态 CSS，没有验证真实 viewport 下的溢出、裁切和交互可达性。

Windows 显示缩放会减少页面可用的 CSS viewport。例如 1366px 宽屏幕在 125% 缩放下约为 1093 CSS px，在 150% 缩放下约为 911 CSS px，正好进入当前死区。浏览器缩小会增加 CSS viewport，因此只是绕过问题，不是正确解决方案。

## 技术取舍

### 采用原生响应式能力

- 全局应用壳层使用 media query，响应浏览器 viewport。
- 业务组件使用 container query，响应扣除侧栏和页面间距后的真实内容宽度。
- 使用 CSS Grid、Flexbox、`minmax()`、`clamp()`、`min-width: 0` 和动态视口单位。
- 业务组件默认使用不溢出的单栏或安全布局，在浏览器支持 container query 时逐级增强为双栏、三栏；不增加生产依赖。
- 不采用 `transform: scale()`、页面级 zoom 或继续扩大固定最小宽度。

### 不迁移管理台框架

CoreUI Vue、Admin One Vue 等 MIT 项目具有成熟的响应式侧栏，但迁移会重写现有 DOM、主题和交互。本项目仅复用其布局思想，不引入框架或复制页面实现。

### 不用全局裁切掩盖问题

删除 `body` 的固定最小宽度。页面级横向溢出必须从产生溢出的组件中消除，不能依赖全局 `overflow-x: hidden` 把错误隐藏。只有明确设计为固定工作台的壳层可以限制自身溢出，并必须为内容提供合法的内部滚动面。

## 全局布局契约

### 页面根节点

- `html`、`body`、`#app` 使用 `width: 100%` 和 `min-width: 0`。
- `body` 允许普通页面自然纵向滚动。
- 登录页、独立实时面试页等不再继承会阻断滚动的全局规则。
- 应用壳层可以固定为 viewport 高度，但主内容区域必须拥有明确的纵向滚动职责。

### 导航分档

| viewport 宽度 | 导航形态 | 正文策略 |
| --- | --- | --- |
| `≥1280px` | 248px 完整侧栏 | 标准页面间距 |
| `1024–1279px` | 216px 紧凑侧栏 | 收紧页面间距，业务组件按容器宽度重排 |
| `<1024px` | 抽屉导航 | 正文获得完整宽度，遮罩和焦点行为完整 |

断点由内容可用空间决定，不代表具体设备型号。电脑在高系统缩放下允许进入抽屉布局。

### 布局 token

全局统一维护以下类型的 token，业务组件不重复计算侧栏或正文宽度：

- 侧栏宽度；
- 页面水平与垂直间距；
- 顶栏最小高度；
- 卡片间距；
- 紧凑模式控件间距；
- viewport 高度回退。

具体值以现有视觉为基准，优先使用 `clamp()` 在宽屏与紧凑 PC 之间平滑变化。

### container query 边界

应用主内容区建立命名的 inline-size containment。业务页面根据自身获得的宽度选择布局，不直接用 `100vw` 推导第三栏宽度。

业务组件可以增加内容驱动的局部断点，但必须：

1. 优先复用布局 token；
2. 在本文件记录原因；
3. 增加对应 viewport 自动化测试；
4. 不重新引入页面级固定最小宽度或无说明的裁切。

第一验收门实际使用的内容断点如下。这里的数值针对组件拿到的可用宽度，而不是显示器型号：

| 范围 | 内容宽度断点 | 布局变化 |
| --- | --- | --- |
| 应用壳层 | viewport `1280px`、`1024px` | 完整侧栏、紧凑侧栏、抽屉导航 |
| 求职助手 | `1240px`、`820px` | 三栏、上下文抽屉、聊天主视图并使用双抽屉 |
| 岗位检索 | `1000px`、`760px` | 紧凑搜索与列表、列表/详情单页切换 |
| 简历助手 | `1100px`、`900px` | 两列紧凑布局、标签式单列工作区 |

简历助手在 `900px` 进入标签式单列，是因为应用壳层扣除页面间距后的内容宽度已经不足以稳定并排呈现文档与助手；该断点避免在 900px 逻辑 viewport 下继续压缩正文。

## 业务页面设计

### 求职助手

- 主任务始终是聊天区。
- 宽容器显示历史记录、聊天和上下文三栏。
- 中等容器保留历史记录与聊天，上下文改为抽屉。
- 窄容器只固定展示聊天，历史记录和上下文分别从明确入口打开。
- 拖动上下文栏只在三栏模式启用；进入抽屉模式后关闭拖动能力，但保留用户之前设置的栏宽。
- 跨断点不重新挂载会话组件，不丢失草稿、选中会话、消息和滚动位置。

### 岗位检索

- 搜索栏从单行切换为两行或自然换行，搜索输入保持优先宽度。
- 结果列表宽度由容器决定，不固定为 370px。
- 宽容器使用列表与详情双栏。
- 窄容器使用列表与详情单页切换；返回列表后保留搜索条件、选中项和滚动位置。
- 多选、扩展连接状态和主要搜索操作始终可见。

### 简历助手

- 搜索表单按容器宽度切换四列、两列和单列。
- 历史记录卡片使用自适应网格，不固定四列。
- 文档与助手工作区在可用宽度足够时双栏展示；不足时使用标签切换，不通过压缩正文宽度维持双栏。
- 固定最小高度改为可滚动或随 viewport 收敛，短屏可以访问底部操作。

### 面经库

- 把依赖全局 viewport 的主布局规则迁移为容器响应。
- 宽容器显示面经树与详情双栏。
- 窄容器使用索引与阅读详情单页切换，返回时保留树节点和滚动位置。
- 导入、采集弹窗继续独立滚动，不超过当前动态 viewport。

### 实时面试

- 准备页在短屏允许自然纵向滚动，不被全局 body 裁切。
- 直播页保持当前问题和回答为最高优先级。
- 转写记录在紧凑高度或宽度下可以折叠或从抽屉查看。
- 直播页只保留一个主要内容滚动面，结束、归档等关键操作始终可访问。

### 登录页

- 删除会阻止短屏访问的 680px 强制下限与页面裁切组合。
- 宽屏保留双栏叙事与认证表单。
- 短屏允许页面自然增长和纵向滚动，认证表单不得被截断。

### 管理页及其他路由

- 卡片和表单优先自动换行或改成单列。
- 表格、时间轴、代码块等不可自然换行的数据结构允许在自己的容器内横向滚动。
- 页面本身不能出现非预期横向滚动。

## 高度与滚动契约

每个路由只保留一个主要纵向滚动面：

- 普通内容页由主内容区滚动；
- 聊天和实时面试工作台由指定内容区内部滚动；
- 弹窗由弹窗主体滚动；
- 表格和代码块可以拥有局部横向滚动。

使用 `100vh` 作为旧行为回退，并在支持时覆盖为 `100dvh` 或更安全的 `100svh`。不允许 `body`、`.main` 与业务组件同时锁高并裁切。短屏优先减少非关键间距和允许滚动，不缩小基础字号。

## 跨断点状态规则

- 调整窗口、系统缩放或浏览器缩放时，只改变布局，不重置业务状态。
- 已输入但未提交的内容必须保留。
- 已选中的会话、岗位、简历记录和面经节点必须保留。
- 进入宽屏后关闭无必要的导航遮罩；返回窄屏时不自动打开抽屉。
- 单页详情返回列表后恢复原列表位置。
- 抽屉支持键盘打开、`Esc` 关闭、遮罩关闭和关闭后的焦点返回。

## 无障碍与交互尺寸

- 浏览器 200% 缩放下核心功能仍可完成，视觉不要求与 100% 完全一致。
- 文字、标签和按钮不得因布局收缩被裁切。
- 不使用 CSS 缩放压缩页面。
- 主要交互控件高度不得低于 40px；仅图标型辅助按钮可以更小，但必须保留清晰焦点样式和可访问名称。
- 焦点顺序与视觉顺序保持一致；抽屉和弹窗管理焦点。
- 保留现有 `prefers-reduced-motion` 行为。

## 验收矩阵

### 逻辑 viewport

自动化直接测试 CSS viewport，不用 `deviceScaleFactor` 代替系统缩放：

- `900 × 420`：高缩放短屏底线；
- `1024 × 600`：紧凑 PC；
- `1093 × 614`：1366×768、Windows 125% 的近似逻辑尺寸；
- `1280 × 720`：标准 PC；
- `1366 × 768`：常见笔记本；
- `1440 × 900`：标准办公屏；
- `1920 × 1080`：全高清；
- `2560 × 1440`：高分辨率宽屏。

浏览器验收覆盖 Chrome、Edge 最新两个大版本，以及浏览器 100%、125%、150%、200% 缩放下的核心流程。Firefox 必须能够加载页面、完成导航、阅读内容和提交普通表单，但不作为像素级截图验收目标，也不承诺依赖浏览器扩展的业务流程。

### 自动化断言

以结构断言为主；稳定截图在视觉基线确定后作为辅助门禁，不阻塞第一验收门：

1. 页面根节点不存在非预期横向溢出；
2. 页面标题、主操作和关键状态位于可访问区域；
3. 主要纵向滚动面可以滚动到最后一项；
4. 抽屉、遮罩、单页详情切换和焦点返回行为正确；
5. 弹窗不超过动态 viewport，底部按钮可访问；
6. 跨断点后输入和选择状态不丢失；
7. 表格等例外只在自身容器出现横向滚动。

Playwright 作为开发依赖，不进入生产包。第一验收门对全局壳层、登录页、求职助手、岗位检索和简历助手执行真实浏览器结构与交互断言；动态消息、时间和任务数据不做全页像素比较。

### 现有验证

改造过程中继续运行：

- 前端全部 Node 测试；
- Vite 生产构建；
- 与改动页面相关的现有布局静态测试；
- 新增 Playwright 多 viewport 测试。

### 第一验收门实施结果（2026-08-27）

- 已完成全局壳层、登录页、求职助手、岗位检索和简历助手的 PC 响应式改造。
- Chromium 覆盖 `900 × 420`、`911 × 512`、`1093 × 614`、`1280 × 720`、`1440 × 900`，验证导航分档、页面级横向溢出、抽屉焦点返回、列表/详情切换及跨布局状态保留。
- Firefox 基础门禁覆盖应用壳层和登录页的加载、导航形态、内容可达性与横向溢出。
- Node 测试 `180/180` 通过，Vite 生产构建通过，Playwright 真实浏览器测试 `7/7` 通过（Chromium `5/5`、Firefox 基础门禁 `2/2`）。
- 本轮未部署生产环境；面经库、实时面试及其余管理路由仍属于第二验收门。

## 实施顺序

### 第一验收门

1. 全局根节点、应用壳层、导航分档、布局 token 和主内容 container；
2. 登录页；
3. 求职助手；
4. 岗位检索；
5. 简历助手；
6. 第一批 Playwright viewport 验证。

第一验收门通过后，再进入其余页面；不在同一轮边修改基础设施边无限扩展页面范围。

### 第二验收门

1. 面经库；
2. 实时面试；
3. 管理页、评测中心、技能页和工作台其余路由；
4. 完整 viewport 矩阵与构建验证；
5. 同步更新本文件中的例外断点、滚动边界和验证结果。

## 非目标

- 不部署生产环境。
- 不重做业务接口、状态管理或权限体系。
- 不迁移 UI 框架。
- 不进行 iPad 或平板专项适配。
- 不在 PC 验收前开展手机端专项视觉重构。
- 不以所有尺寸像素完全一致为目标；以内容可达、主任务清晰和交互完整为目标。

## 完成标准

以下条件全部满足后，PC 多屏幕响应式改造才算完成：

1. 用户在目标矩阵内无需 `Ctrl + -` 即可完成核心操作；
2. 所有路由不存在非预期页面级横向溢出；
3. 高缩放短屏下不存在因锁高和裁切而无法访问的关键内容；
4. 复杂页面按批准的优先级收纳辅助区域；
5. 跨断点不丢失业务状态；
6. 现有测试、生产构建和新增 viewport 自动化测试全部通过；
7. 响应式布局规则、例外和验证结果与实现同步更新。
